# MCP-сервер для 1С-Битрикс (только чтение)

Даёт языковой модели читать данные сайта по протоколу
[MCP](https://modelcontextprotocol.io) — каталог, разделы, свойства товаров.
**Записи в модуле нет**: не отключена настройкой, а отсутствует в коде.

Требования: 1С-Битрикс 22+, PHP 8.0+, модуль `iblock`.
Проверено на Битрикс 26.650.0 / PHP 8.5 / Apache.

## Чем отличается от готовых решений

- **не выполняется на страницах сайта.** Запросы приходят на отдельную точку
  входа `/mcp/index.php`; обработчиков событий модуль не регистрирует вовсе.
  Решения, ловящие MCP-запросы в `OnProlog`, работают на каждом хите витрины;
- **белый список.** Инфоблоки и свойства выбираются в админке. Чего в списке
  нет — того для модуля не существует, произвольный фильтр не принимается;
- **токен показывается один раз** и хранится хешем;
- **журнал каждого обращения**, включая отвергнутые.

## Установка

1. Положить папку в `local/modules/itb.mcp/`.
2. Админка → Marketplace → Установленные решения → «MCP-сервер (только чтение)»
   → Установить. Создаются две таблицы и точка входа `/mcp/index.php`.
3. Настройки → Настройки продукта → Настройки модулей → **MCP-сервер**.

Если установка отказала — откройте `/mcp/check.php` (только для администратора):
страница проходит путь до модуля по шагам и говорит, где именно теряет.

## Настройка

**Вкладка «Токены».** Кнопка «Выпустить» → значение показывается один раз, там же
готовая строка подключения. По умолчанию срок полгода; очистить поле — токен
станет бессрочным. Пока токенов нет, сервер не отвечает никому.

**Вкладка «Данные».** Галочка на инфоблок — его можно читать. Поле «свойства»
необязательное: пусто — отдаются все свойства, через запятую — только
перечисленные коды.

> Инфоблоки с персональными данными (заказы, обращения, подписки) открывать не
> стоит: читает их не человек, и ответы уходят за пределы сайта. То же касается
> свойств с себестоимостью и закупочными ценами.

**Вкладка «Настройки».** Разрешённые `Origin` (пусто — браузерам нельзя вовсе,
это верное значение по умолчанию) и срок хранения журнала.

## Подключение клиента

```
claude mcp add --transport http bitrix https://САЙТ/mcp/ \
  --header "Authorization: Bearer ВАШ_ТОКЕН"
```

Токен передаётся заголовком. В адресе он не принимается: адреса оседают в логах
веб-сервера, в истории и в реферере.

## Инструменты

| Инструмент | Что делает |
|---|---|
| `site_info` | версия Битрикса, модули, открытые инфоблоки и их свойства |
| `element_search` | поиск по названию, коду, разделу, активности, значениям свойств |
| `element_get` | один элемент со всеми заполненными свойствами |
| `section_list` | дерево разделов инфоблока |
| `order_search` | заказы: номер, статус, даты, оплата, отмена |
| `order_get` | заказ целиком: корзина и свойства с данными покупателя |
| `order_statuses` | коды статусов этого магазина и их названия |

Инструменты каталога появляются, только когда открыт хотя бы один инфоблок.

Инструменты делятся на группы — **каталог**, **заказы**, **разведка API**.
Каждая включается в настройках модуля и отдельно выдаётся токену: одному можно
дать только каталог, другому — каталог и заказы, третьему — одну разведку API.

> ⚠️ Группа «заказы» по умолчанию выключена: в свойствах заказа лежат имя,
> телефон и адрес покупателя, и `order_get` отдаёт их наружу.

`element_search` **не возвращает свойства**, пока их не назовут в `props`:
на живом каталоге карточка без свойств весит 398 байт, со всеми 138 — 17,6 КБ,
и выдача из двадцати строк доходила до 750 КБ.

### Два движка чтения

По умолчанию — ORM. Настройка «Читать через ORM (D7)» переключает способ
выборки; в каждом ответе есть поле `engine`, по которому видно, каким путём
получены данные.

| | `legacy` (`CIBlockElement`) | `orm` (`ElementXxxTable`) |
|---|---|---|
| свойства | запрос на каждый элемент | вместе с элементами |
| 50 элементов, 1 свойство | 0,41 с | 0,27 с |
| 50 элементов, 5 свойств | 0,38 с | 0,51 с |
| карточка со 138 свойствами | работает | работает |
| нужен `API_CODE` у инфоблока | нет | да |

ORM выигрывает, когда свойств просят мало, и проигрывает на нескольких: каждое
одиночное свойство — это JOIN. Свойства режутся на пачки по 30, иначе MySQL
отказывает («Too many tables», предел 61 таблица в соединении).

Инфоблок без `API_CODE` сущности не даёт — там модуль сам откатывается на
`legacy`, настройка при этом ни на что не влияет.

⚠️ Одно отличие в поведении: отбор по разделу в `orm` идёт по **основному
разделу элемента**, а `legacy` смотрит ещё и таблицу связей. На живом каталоге
это дало 9098 против 9097. Инструмент говорит об этом в ответе.

## Протокол

Streamable HTTP, версии `2025-06-18` и `2025-03-26`. Ответ — обычный
`application/json`, SSE не используется; `GET` и `DELETE` отвечают `405`;
сессий нет. Проверяется `Origin`, чужой `MCP-Protocol-Version` даёт `400`,
уведомление — `202` без тела.

## Разработка

```
php tests/protocol.php    # транспорт, рукопожатие, инструменты, JSON-RPC
php tests/tokens.php      # выпуск, срок, отзыв, белый список инструментов
php tests/expose.php      # разбор белого списка инфоблоков
```

Тесты не требуют ни Битрикса, ни базы: `Protocol`, `Transport`, `Schema`,
`Token`, `Expose` от них не зависят. Битрикс начинается в `Server` (сбор
запроса), `Data` (каталог) и `Orm/` (таблицы).

## Что модуль не делает

Не пишет, не удаляет, не выполняет произвольные запросы, не отдаёт файлы,
не работает с заказами и пользователями. Всё это — за пределами задачи «дать
модели прочитать каталог».
